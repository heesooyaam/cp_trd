# Прагмы для контеста (GCC, C++20)

Печатная памятка находится в разделе Various. Сначала измеряйте решение без дополнительных прагм. Ускорение зависит от компилятора, CPU и того, какие операции занимают время.

Для массовых операций с битсетами на **поддерживающем эти инструкции x86**:

~~~cpp
#pragma GCC optimize("O3,unroll-loops")
#pragma GCC target("avx2,popcnt")
#include <bits/stdc++.h>
~~~

Именно такой набор обсуждается в [блоге Chilli про bitset](https://codeforces.com/blog/entry/77480). Это старый эксперимент, а не обещание конкретного ускорения на нынешнем судье. Хак с переопределением системных макросов из того поста в справочник не включён.

| Опция | Когда проверять |
|---|---|
| popcnt | Частые count() / __builtin_popcountll |
| avx2 | Длинные циклы по словам, AND/OR/XOR |
| O3 | Горячие циклы; больше преобразований, чем O2 |
| unroll-loops | Маленькое тело цикла; может ухудшить instruction cache |
| bmi,bmi2,lzcnt | Конкретные битовые операции, не обязательная часть bitset-набора |
| fma | Вещественное умножение со сложением; не ускоритель bitset |

В [разборе nor](https://nor-blog.pages.dev/posts/2021-10-26-gcc-optimization-pragmas/) и его [переводе на CF](https://codeforces.com/blog/entry/129283) разобраны типичные ошибки синтаксиса. Пишите GCC, а не gcc, optimize, а не optimization, и без пробела внутри строки перед опцией. Прагмы действуют на последующие определения функций; для шаблонов стандартной библиотеки ставьте общий набор до заголовков.

AVX2 разрешает SIMD, но не гарантирует, что конкретный цикл векторизуется, и не содержит обычной векторной инструкции popcount. target разрешает инструкции, а не проверяет CPU при запуске. Неподдерживаемая инструкция может завершить программу. arch=native ориентируется на машину компиляции, которая может отличаться от машины запуска. [GCC: x86 options](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html).

Ofast включает fast-math; это допускает преобразования, меняющие результаты вещественных вычислений. Для дерева окружностей и другой геометрии оставляем обычную арифметику. O3 само по себе не включает fast-math. Старое утверждение «O2 вообще не векторизует» уже не годится для современных GCC. [GCC: optimization options](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html).

Локальная настройка:

~~~cpp
#pragma GCC push_options
#pragma GCC optimize("O3")
#pragma GCC target("popcnt")
void hot_function() { /* ... */ }
#pragma GCC pop_options
~~~

push_options сохраняет настройки, pop_options возвращает предыдущие; reset_options возвращает настройки командной строки. [GCC: function-specific pragmas](https://gcc.gnu.org/onlinedocs/gcc/Function-Specific-Option-Pragmas.html).

#pragma GCC unroll 4 ставят непосредственно перед выбранным циклом. ivdep — обещание программиста об отсутствии зависимостей между итерациями, мешающих SIMD, а не безусловное «сделать быстрее». Его нельзя механически добавлять в DP. [GCC: loop pragmas](https://gcc.gnu.org/onlinedocs/gcc/Loop-Specific-Pragmas.html).

Практическая проверка: максимальные входы, один и тот же seed, несколько запусков и одинаковый checksum. Сравните O2, O2+popcnt, O3+avx2+popcnt, затем добавьте unroll-loops. Отдельно измеряйте .count() и логические операции: у них разные узкие места. В doc/benchmarks/bitset.cpp есть воспроизводимый пример; он не включён в постоянный шаблон решения.
